# ביצועים – מדידות על 100,000 פניות

המסמך מתעד איך נבדקה יעילות הפעולות המרכזיות, מה נמצא, מה תוקן, ואיפה צווארי הבקבוק. כל מספר כאן נמדד, ואפשר להריץ את המדידה שוב (ראו [הרצה חוזרת](#הרצה-חוזרת)).

## איך נמדד

* **נתונים:** 100,000 פניות וכ־140,000 שורות היסטוריה, מה־Seeder הדטרמיניסטי (אותם נתונים בכל הרצה), אחרי בנייה מחדש של האינדקסים ועדכון סטטיסטיקות.
* **אותן שאילתות ש־EF Core שולח:** הקובץ [`performance/measure.sql`](performance/measure.sql) כתוב בדיוק כמו ה־SQL ש־EF Core 10 מייצר: `sp_executesql` עם פרמטרים מוקלדים, כך שה־Optimizer רואה את מה שהוא רואה בפועל. ה־SQL האמיתי נלכד מהלוג של ה־API בזמן המדידה ([`ef-sql.log`](performance/runs/3-search-text/results/ef-sql.log)) לצורך השוואה.
* **שלושה מדדים:**
  * **Logical reads** (`SET STATISTICS IO`): מספר דפי ה־8KB שהשאילתה קראה. זה המדד העיקרי: הוא לא תלוי בעומס על המכונה, ולכן אפשר להשוות בין הרצות.
  * **CPU** ו־**Elapsed** (חציון של 5 הרצות "חמות", אחרי הרצת חימום).
  * **Execution Plan בפועל** (`SET STATISTICS XML`), שמור כקובץ `.sqlplan` שנפתח ב־SSMS.
* **כל תרחיש נמדד במצבים שונים:** עם כל האינדקסים; בלי אף אינדקס משני; ו**עם כל האינדקסים חוץ מאחד**, לכל אינדקס בנפרד. כך רואים בדיוק מה כל אינדקס שווה, ואינדקס שלא עוזר לאף תרחיש היה מוסר.
* **זמני API מקצה לקצה:** 20 קריאות לכל נקודת קצה, אחרי 3 קריאות חימום ([`api-timings.md`](performance/runs/3-search-text/results/api-timings.md)).
* **סביבה:** GitHub Actions runner ‏(4 vCPU, ‏16GB), ‏SQL Server 2022 Developer וה־API ב־Docker. זמני CPU במכונה משותפת משתנים בין הרצות (למשל אותו Sort עמוק: 326ms בהרצה אחת ו־561ms בשנייה), ולכן ההשוואות מבוססות על Logical reads.

## איך נמנעת טעינת כל הנתונים לזיכרון

* כל שאילתה נבנית כ־`IQueryable` ורצה כולה ב־SQL Server: `WHERE` לפי הסינונים, `ORDER BY` לפי שדה מרשימה סגורה, `OFFSET/FETCH`, והטלה (`Select`) רק לעמודות שבתשובה. רק העמוד המבוקש (עד 100 שורות) יוצא מבסיס הנתונים. ב־`ef-sql.log` רואים שאין אף שאילתה בלי `OFFSET/FETCH`, `TOP` או `GROUP BY`.
* מספר העמודים מגיע מ־`COUNT(*)` נפרד עם אותם סינונים. עמוד שאחרי הסוף מוחזר ריק בלי שאילתת העמוד.
* הנתונים המסכמים הם `GROUP BY` בבסיס הנתונים: עד 7 שורות חוזרות.
* הלקוח לא מסנן, לא ממיין ולא מדפדף בעצמו.

## מה המדידה הראשונה גילתה – ומה תוקן

בגרסה הראשונה האינדקסים היו, למשל, `(CreatedAt DESC)` ו־`(Status, CreatedAt DESC)`. הספירות השתמשו בהם, אבל **שאילתת העמוד** (20 השורות) סרקה את כל הטבלה ומיינה אותה. ב־Execution Plan: ‏`Sort → Clustered Index Scan` (‏[`list-default.indexed.2.sqlplan`](performance/runs/1-initial/plans/list-default.indexed.2.sqlplan)).

**הסיבה:** הרשימה ממוינת `ORDER BY CreatedAt DESC, Id DESC` (‏`Id` שובר שוויון, כדי שהדפדוף יהיה יציב). אינדקס משני ב־SQL Server מחזיק את מפתח ה־Clustered (`Id`) **בסדר עולה**, כך שסדר האינדקס היה `CreatedAt DESC, Id ASC`. הסדר הזה לא תואם את ה־ORDER BY, ולכן כדי להחזיר 20 שורות היה צריך למיין את כל השורות המתאימות. במצב כזה ה־Optimizer העדיף לסרוק את הטבלה.

**התיקון** (Migration `TuneIndexes`): כל אינדקס שמשרת את הרשימה מסתיים במפורש ב־`CreatedAt DESC, Id DESC`. עכשיו SQL Server קורא את האינדקס בסדר הנכון ועוצר אחרי 20 שורות (`Index Seek → Clustered Index Seek` ל־20 שורות בלבד). אותו אינדקס משרת גם את המיון ההפוך (הישנות קודם) בקריאה לאחור.

**מחיר האינדקסים בכתיבה:** עדכון סטטוס משנה את `Status` ואת `UpdatedAt`, ולכן מעדכן רק את האינדקסים שמכילים את `Status` (שלושה). `Title` ו־`OrganizationName` לא משתנים אחרי יצירת הפנייה, כך שהאינדקסים עליהם, וגם `SearchText` שנגזר מהם, לא עולים כלום בעדכונים. עדכון סטטוס עצמו הוא `UPDATE` לפי מפתח ראשי (Clustered Index Seek) ו־`INSERT` אחד להיסטוריה.

**אינדקסים שלא נוספו בכוונה:** אין אינדקס לכל עמודת מיון (עדכון אחרון, כותרת, עדיפות). מיון כזה ממיין את כל השורות (~150ms CPU על 100,000), והוא פעולה פחות נפוצה מהמיון ברירת המחדל. אינדקס לכל מיון היה מכפיל את המקום ואת עלות הכתיבה בשביל מקרה שולי.

## החיפוש החופשי: מצוואר בקבוק לשיפור מדוד

**מה נמדד במצב הקודם:** `Title LIKE '%היתר%' OR OrganizationName LIKE '%היתר%'`: ‏2,502 reads, ‏~306ms CPU בבסיס הנתונים, ‏315ms ב־API, פי 30 מכל פעולה אחרת ברשימה.

**למה:** תבנית שמתחילה ב־`%` לא יכולה להשתמש באינדקס (אין "התחלה" לחפש ממנה), כך שה־`COUNT(*)` סורק את כל הטבלה. רוב הזמן הוא CPU של השוואת מחרוזות: ה־Collation הרגיל משווה לפי כללי שפה (רישיות, ניקוד, תווים מיוחדים), וזה יקר לכל אחת מ־100,000 השורות.

**הפתרון שמומש** (Migrations ‏`AddSearchText` ו־`SearchTextInIndexOnly`, ‏[`ServiceRequestConfiguration`](../backend/src/RequestsManagement.Infrastructure/Persistence/Configurations/ServiceRequestConfiguration.cs)):

```sql
SearchText AS CAST(UPPER(Title + NCHAR(31) + OrganizationName) AS nvarchar(401)) COLLATE Latin1_General_100_BIN2
IX_Requests_CreatedAt_Id (CreatedAt DESC, Id DESC) INCLUDE (SearchText)
-- החיפוש: WHERE SearchText LIKE '%' + UPPER(@term) + '%'
```

* **עמודה מחושבת:** SQL Server מחשב אותה בעצמו מהכותרת ומהארגון, כך שהיא לא יכולה לצאת מסנכרון איתם ואין קוד שצריך לעדכן אותה. בקוד היא Shadow Property: קיימת בבסיס הנתונים ובשאילתה, אבל לא בישות `ServiceRequest`, כי היא פרט טכני של החיפוש.
* **Collation בינארי:** השוואת בתים במקום כללי שפה. כאן רוב החיסכון.
* **`UPPER` בשני הצדדים:** החיפוש נשאר לא רגיש לאותיות גדולות/קטנות באנגלית, כמו קודם (בעברית אין רישיות). השוואה שרגישה לניקוד הייתה גם קודם, כך שבעברית ההתנהגות זהה.
* **מפריד `NCHAR(31)`** בין הכותרת לארגון: תו בקרה שאי אפשר להקליד (והוולידציה דוחה תווי בקרה בחיפוש), כך שחיפוש לא ימצא התאמה "על הגבול" בין סוף הכותרת לתחילת שם הארגון.
* **לא `PERSISTED`:** הערך נשמר רק באינדקס, המקום היחיד שקורא אותו (ראו למטה).

**מה המדידה לפני המימוש גילתה** ([פירוט הניסויים](performance/runs/3-search-text/index-options/README.md)):
1. ההצעה המקורית, אינדקס נפרד על `SearchText`, הוזילה את ה־`COUNT`, אבל **שאילתת העמוד** נשארה עם אותה תוכנית: לקרוא את הפניות מהחדשה לישנה ב־`IX_Requests_CreatedAt_Id`, ולכל שורה לקפוץ לטבלה (Lookup) כדי לבדוק את הטקסט, עד שנמצאות 20 התאמות. במילה נפוצה זה זול, אבל **במילה נדירה** (שם של ארגון אחד, ~200 התאמות) אלה עשרות אלפי קפיצות: **45,590 reads** גם בחיפוש הקודם, ו־44,848 עם האינדקס הנפרד. הבעיה הזו הייתה קיימת ולא נראתה, כי המדידה המקורית בדקה רק מילה נפוצה.
2. **הפתרון:** להכניס את `SearchText` ל־`IX_Requests_CreatedAt_Id` עצמו (`INCLUDE`). עכשיו שאילתת העמוד קוראת את האינדקס בסדר הרשימה ובודקת את הטקסט בתוכו, בלי קפיצות: מילה נפוצה עוצרת אחרי 20 התאמות, ומילה נדירה סורקת לכל היותר את האינדקס הזה. גם ה־`COUNT` סורק אותו. זה ניצח בכל מקרה שנבדק את האינדקס הנפרד, ואת האינדקס הנפרד עם רמז שמבטל את ה־Row Goal, והוא גם הפשוט מהשלושה: אין אינדקס נוסף ואין רמזים בשאילתה.
3. **PERSISTED או לא:** בהרצה מלאה עם עמודה `PERSISTED` כל סריקה מלאה של הטבלה גדלה מ־1,916 ל־3,070 reads (‏+60%), כי הטבלה החזיקה עותק של הכותרת ושל הארגון. בגרסה הסופית העמודה לא נשמרת בטבלה, והערך שלה קיים רק באינדקס. כך הטבלה לא גדלה, והחיפוש מהיר באותה מידה.

**התוצאה** (בבסיס הנתונים: אותה מכונה ואותה הרצה, השאילתה הקודמת רצה כניסוי; ב־API: הרצה 2 מול הרצה 3):

| | לפני | אחרי |
|---|---:|---:|
| מילה נפוצה ("היתר"), בבסיס הנתונים | 2,445 reads · ‏356ms CPU | **1,394 reads · ‏26ms CPU** |
| מילה נדירה (שם ארגון), בבסיס הנתונים | 45,590 reads · ‏418ms CPU | **1,578 reads · ‏31ms CPU** |
| מילה נפוצה, ב־API | 315ms | **31ms** |

**המחיר:** האינדקס `IX_Requests_CreatedAt_Id` גדל (נוסף לו עותק של הכותרת והארגון, בסדר גודל של 10–15MB ל־100,000 פניות). אין עלות בעדכוני סטטוס, כי הכותרת והארגון לא משתנים. החיפוש עדיין סורק (עכשיו אינדקס אחד, בהשוואת בתים), כך שהזמן שלו גדל ליניארית עם הטבלה.

**נבדק בבדיקות:** אותן תוצאות בדיוק כמו החיפוש הקודם (`Search_matches_title_or_organization` משווה מול `Title.Contains || OrganizationName.Contains`), אין התאמה על הגבול בין הכותרת לארגון, ואותיות לטיניות נמצאות בלי תלות ברישיות.

**למה עמודה נפרדת ולא שינוי של העמודות הקיימות:** העמודה היא עותק נגזר שמשמש רק לחיפוש. `Title` ו־`OrganizationName` נשארים כמו שהם, ומהם המערכת מציגה, ממיינת ומסננת. אם היינו משנים את ה־Collation של `Title` עצמה לבינארי, המיון לפי כותרת היה מסדר לפי קוד התווים ולא אלפביתית, וסינון בשוויון היה הופך רגיש לאותיות גדולות/קטנות. `UPPER` על העמודה המקורית היה משנה את הטקסט שהמשתמש רואה.

### הפתרון המלא: Full-Text Search

**איך זה עובד:** אינדקס רגיל ממוין לפי תחילת הערך, ולכן לא עוזר לחפש מילה באמצע הכותרת. Full-Text Search בונה **אינדקס הפוך**: הוא מפרק כל כותרת למילים ושומר לכל מילה את רשימת השורות שבהן היא מופיעה (כמו אינדקס בסוף ספר). החיפוש ניגש ישר לרשימה של המילה ולא סורק את הטבלה, כך שהזמן כמעט לא תלוי בגודל הטבלה.

```sql
CREATE FULLTEXT CATALOG RequestsCatalog;
CREATE FULLTEXT INDEX ON dbo.Requests (Title LANGUAGE 1037, OrganizationName LANGUAGE 1037)  -- 1037 = עברית
    KEY INDEX PK_Requests ON RequestsCatalog WITH CHANGE_TRACKING AUTO;

SELECT ... FROM dbo.Requests WHERE CONTAINS((Title, OrganizationName), N'"היתר*"');   -- EF Core: EF.Functions.Contains
```

**מה מקבלים:** חיפוש כמה מילים ביחד (`היתר AND העסקה`), מילים קרובות, תחילת מילה (`"היתר*"`), ודירוג רלוונטיות (`CONTAINSTABLE`).

**המחירים, ולמה זו החלטה מוצרית ולא רק טכנית:**
1. **חיפוש מילים, לא "מכיל":** חלק ממילה (`תר`) לא ימצא את "היתר". בעברית, עם אותיות השימוש (ל־, ב־, ה־), לא מובטח ש"היתר" ימצא את "להיתר"; צריך לבדוק את מפרק המילים העברי על הנתונים האמיתיים. ההתנהגות שונה מה־`LIKE` של היום.
2. **עדכון לא מיידי:** האינדקס מתעדכן ברקע (`CHANGE_TRACKING AUTO`), ופנייה חדשה עשויה להופיע בחיפוש רק אחרי כמה שניות.
3. **רכיב נוסף לתחזוקה:** קטלוג, אינדקס ושירות רקע.

**למה לא נמדד כאן:** ה־Image הרשמי של SQL Server ל־Linux (`mssql/server:2022-latest`) לא כולל את רכיב ה־Full-Text. כדי להשתמש בו צריך Image מותאם (Dockerfile שמתקין את `mssql-server-fts`), כלומר שלב בנייה נוסף לכל מי שמריץ את הפרויקט. ב־SQL Server על Windows וב־Azure SQL הוא זמין מובנה.

**המלצה:** בגודל הנוכחי, העמודה המחושבת (שמומשה) שומרת בדיוק על ההתנהגות ("מכיל") ומספיקה. כשהנתונים גדלים למיליונים, וכשרוצים חיפוש מילים עם דירוג, Full-Text Search הוא השלב הבא, עם המחירים שלמעלה.

## ממצאים נוספים

* **מיון בלי אינדקס ודפדוף עמוק:** מיון לפי כותרת או עדכון אחרון ממיין את כל 100,000 השורות (‏1,916 reads, ‏150–560ms CPU). בעמוד 500 ה־`OFFSET` מדלג על 49,900 שורות ממוינות. **שיפור שנמדד** (`experiment.deep-page-keyset`): ‏Keyset Pagination, כלומר "המשך אחרי השורה האחרונה שראית" (`WHERE (Title, Id) > (@lastTitle, @lastId)`) עם אינדקס `(Title, Id)`: **333 reads ו־~0ms** במקום 1,916 reads ו־~560ms. המחיר: אין קפיצה ישירה לעמוד N, ונדרש אינדקס לכל סדר מיון שרוצים לתמוך בו כך.
* **ארגון (מתחיל ב־) אחרי שינוי האינדקס:** בהרצה הסופית ה־Optimizer בחר לתרחיש הזה תוכנית אחרת: סריקת הטבלה ומיון (1,857 reads, ‏38ms ב־API) במקום קריאת `IX_Requests_CreatedAt_Id` עם קפיצות לטבלה (1,059 reads, ‏7ms). הסיבה: האינדקס הזה גדל (הוא מחזיק עכשיו את `SearchText`), וההערכה של עלות סריקתו עלתה מעל עלות סריקת הטבלה. 38ms עדיין מהיר, ולכן זה מתועד ולא תוקן. תיקון אפשרי: לסנן את הארגון בשוויון כשנבחר שם מלא מהרשימה (Seek ישיר על `IX_Requests_OrganizationName_CreatedAt_Id` בסדר הרשימה, בלי מיון), ולהשאיר "מתחיל ב־" רק לטקסט חופשי.
* **`COUNT(*)` בכל בקשה:** מתוך 221 ה־reads של הרשימה ללא סינון, ~150 הם הספירה (סריקת האינדקס הצר ביותר). זה גדל ליניארית עם הטבלה. שיפור: ספירה משוערת מ־`sys.dm_db_partition_stats` כשאין סינון, או החזרת "יש עוד" במקום מספר מדויק.
* **Lookups:** ‏~45ms, בגלל `DISTINCT` על 100,000 שורות. הרשימות כמעט לא משתנות, ולכן הן מועמדות טבעיות ל־Cache נוסף אם יידרש.

## הרצה חוזרת

**אוטומטית** (כמו ב־CI): כשהמערכת רצה (`docker compose up -d --build`):

```bash
python3 scripts/perf/measure.py            # כל המצבים: עם/בלי כל אינדקס + ניסויים (~5 דקות)
python3 scripts/perf/measure.py --quick    # רק עם אינדקסים ובלי אינדקסים
python3 scripts/perf/api_timings.py        # זמני API
```

התוצאות נכתבות ל־`docs/performance/results/` ול־`docs/performance/plans/`. ב־GitHub, דחיפה של ענף `tools/perf-<שם>` מריצה את כל המדידה על מכונה נקייה ([`perf.yml`](../.github/workflows/perf.yml)) ומחזירה את התוצאות לענף.

**ידנית ב־SSMS:** מתחברים ל־`localhost,14333`, פותחים את [`performance/measure.sql`](performance/measure.sql), מפעילים **Include Actual Execution Plan** (Ctrl+M) ומריצים את כל הקובץ או תרחיש אחד. בלשונית Messages מופיעים ה־reads וה־CPU, ובלשונית Execution plan התוכנית.
